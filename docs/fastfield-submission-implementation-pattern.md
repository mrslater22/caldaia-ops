# FastField Form Submission Implementation Pattern

**Reference implementation:** Site Onboarding  
**FastField form:** `1244818` — Site Onboarding, version 10  
**Purpose:** Provide a repeatable implementation pattern for Inspection,
Device, and future FastField form submissions.

## 1. Responsibility Boundaries

FastField is responsible for field data collection, offline operation, form
workflow, and report generation.

BoilerOps is responsible for:

- Authenticating inbound submissions
- Preserving the original submission payload
- Mapping external fields to the domain model
- Maintaining stable entity identities
- Creating and updating Supabase records
- Generating QR assets
- Synchronizing flattened lookup rows back to FastField Data Tables
- Exposing administrative status and retry controls

## 2. End-to-End Site Onboarding Flow

1. A user completes the Site Onboarding form in FastField.
2. FastField sends JSON to:

   `POST /api/fastfield/submissions`

3. BoilerOps validates the configured webhook secret.
4. The form is resolved by FastField form ID or form name.
5. The original JSON is stored in `integration_events.payload_json`.
6. The `site_onboarding` mapper validates and normalizes the form fields.
7. BoilerOps finds or creates the canonical `sites` record.
8. A stable BoilerOps Site ID is assigned.
9. A site QR image is generated and stored in Supabase Storage.
10. A flattened Site Info row is prepared for FastField synchronization.
11. Processing and synchronization status are stored separately from the raw
    payload.
12. The endpoint returns the Site ID, QR routes, and sync status.

## 3. Source Payload Contract

The validated Site Onboarding payload uses these keys:

- `formId` → FastField form identity
- `formVersion` → source form version
- `submissionId` → submission idempotency identity
- `updatedAt` → source update timestamp
- `site_id` → FastField/source site identifier
- `site_code` → human-recognizable 3–4 character site code
- `va_loc` → facility name
- `va_contact` → primary contact name
- `va_contact_email` → primary contact email
- `va_contact_phone` → primary contact phone
- `bo_siteid` → stable BoilerOps ID on update forms

New Site Onboarding submissions normally omit `bo_siteid`. BoilerOps generates
it and publishes it to the Site Info Data Table. Subsequent update forms must
return it.

## 4. Form Registration

Inbound forms are registered in `fastfield_forms`.

The Site Onboarding migration seeds:

- FastField form ID: `1244818`
- Name: `Site Onboarding`
- Purpose: `site_onboarding`
- BoilerOps-to-FastField field mappings
- Active status

Code:

- Form registry migration:
  `supabase/migrations/20260813_site_onboarding.sql`
- Form resolution:
  `apps/boilerops/src/lib/fastfield/ingest.ts`
- Admin registry:
  `/admin/fastfield-forms`

Every new form must have a unique purpose. Do not route unrelated payloads
through a generic fallback mapper.

## 5. Inbound Authentication

Environment setting:

```dotenv
FASTFIELD_WEBHOOK_SECRET=
```

FastField sends this secret using Basic Authentication or the
`x-boilerops-secret` header.

The inbound secret is generated by Caldaia. It is not the FastField outbound
API subscription key.

Code:

`apps/boilerops/src/lib/fastfield/ingest.ts`

Production requirements:

- Require a non-empty webhook secret
- Use HTTPS
- Keep the secret in Vercel environment settings
- Never store it in Git or Supabase configuration rows

## 6. Immutable Integration Event

Every accepted submission is written to `integration_events` before domain
mapping.

Important fields:

- `source_system`
- `event_type`
- `external_id`
- `fastfield_form_id`
- `idempotency_key`
- `payload_json`
- `status`
- `error_message`
- `processed_at`
- `result_json`

`payload_json` preserves the source submission. BoilerOps processing output is
stored in `result_json`; it must not be merged into the source payload.

The Site Onboarding idempotency key follows:

`fastfield:site_onboarding:{submissionId}`

## 7. Mapper Layer

The mapper converts FastField-specific field names into a typed domain input.

Code:

`apps/boilerops/src/lib/fastfield/site-onboarding-mapper.ts`

Responsibilities:

- Read configured field mappings first
- Support validated aliases when appropriate
- Normalize the site code to uppercase
- Validate the 3–4 character site-code format
- Convert blank values to `null`
- Apply the default timezone
- Reject payloads missing required identity fields

The mapper must not write to Supabase or call FastField.

For each future form, create a dedicated mapper and mapped result type instead
of adding unrelated fields to the Site Onboarding mapper.

## 8. Domain Persistence and Identity Matching

Reusable site persistence is implemented in:

`apps/boilerops/src/lib/sites/service.ts`

Site Onboarding searches for an existing site in this order:

1. `bo_siteid` / `sites.public_id`
2. FastField `site_id` / `sites.fastfield_source_site_id`
3. Organization plus `site_code`

If an update form supplies an unknown `bo_siteid`, BoilerOps rejects the
submission instead of creating a duplicate.

The service updates current site details while preserving:

- Internal UUID
- Public BoilerOps ID
- Existing relationships
- QR link identity
- Inspection history

Database migration:

`supabase/migrations/20260813_site_onboarding.sql`

## 9. Identifier and QR Rules

The site has separate identifiers:

- `sites.id`: internal Supabase UUID
- `sites.public_id`: immutable external BoilerOps ID
- `sites.site_code`: mutable human-readable code such as `CAP`

The QR encodes:

`https://{app-host}/i/site/{public_id}`

Code:

- QR generation: `apps/boilerops/src/lib/qr.ts`
- Storage path: `qr-codes/sites/{public_id}.png`
- Site JSON: `GET /i/site/{public_id}`
- QR PNG: `GET /i/site/{public_id}/qr`

Human-readable codes must not be used as QR route identities because they may
change.

## 10. Outbound FastField Data Table Projection

Supabase remains normalized. FastField Data Tables receive flattened lookup
rows.

The Site Info projection currently contains:

```json
{
  "bo_siteid": "site_...",
  "bo_qrcode": "https://boilerops.vercel.app/i/site/site_...",
  "site_code": "CAP",
  "va_loc": "Cape Coral VA Medical Center",
  "va_contact": "John Doe",
  "va_contact_email": "johndoe@va.gov",
  "va_contact_phone": "239-555-5555"
}
```

Configuration is stored in `fastfield_data_tables`. Per-entity status is stored
in `fastfield_sync_records`.

Code:

- Sync projector and request:
  `apps/boilerops/src/lib/fastfield/site-table-sync.ts`
- Admin configuration:
  `/admin/fastfield-data-tables`
- Migration:
  `supabase/migrations/20260814_fastfield_data_table_config.sql`

Credentials remain in protected environment variables.

### Current upsert limitation

True FastField row upsert is not yet verified. The current implementation sends
one configured request and records the response. It does not yet search by
`bo_siteid` and choose create versus update.

After receiving FastField's Data Tables API documentation, implement either:

1. Native upsert using the configured unique key, or
2. Find by stable BoilerOps ID, update the returned record ID, and create only
   when no record exists.

Do not treat repeated POST requests as proven idempotent until this is
validated.

## 11. Submission Response

A processed Site Onboarding response follows:

```json
{
  "ok": true,
  "duplicate": false,
  "purpose": "site_onboarding",
  "site_public_id": "site_...",
  "fastfield_sync_status": "pending",
  "urls": {
    "site": "https://boilerops.vercel.app/i/site/site_...",
    "site_qr": "https://boilerops.vercel.app/i/site/site_.../qr"
  }
}
```

Domain persistence may succeed while outbound FastField synchronization remains
pending or failed. The sync status must not conceal a successfully stored site.

## 12. Administration

Site management:

`/admin/sites`

Administrators can:

- Create and edit sites
- View stable IDs
- Review synchronization status and errors
- Retry FastField synchronization
- View, regenerate, and download QR codes

Data Table configuration:

`/admin/fastfield-data-tables`

Administrators can:

- Configure the three permitted FastField Data Tables
- Set table IDs and row endpoints
- Set HTTP methods and upsert keys
- Edit field mappings
- Activate or deactivate synchronization

Deletion is intentionally omitted where it could destroy relationships or sync
history.

## 13. Error and Retry Behavior

The ingestion event progresses through:

- `received`
- `processed`
- `failed`

Mapping or persistence failures store an error on the integration event.
Administrators can inspect and reprocess events from `/admin/submissions`.

Outbound synchronization separately records:

- `pending`
- `synced`
- `failed`
- `disabled`

This separation prevents a temporary FastField API failure from losing the
canonical Supabase record.

## 14. Pattern for Implementing Another Form

Use this sequence for Inspection Target, Device, and Inspection submissions.

### Step 1: Capture a representative payload

Send the form to:

`POST /api/fastfield/sample`

Capture:

- Required and optional fields
- Repeating sections
- Empty values
- Update/resubmission behavior
- Form ID and version
- FastField-generated row identities
- Attachments and result structures

### Step 2: Confirm the domain boundary

Decide whether the submission creates:

- A persistent master record
- A historical event
- Child records
- Many-to-many relationships
- Documents or observations

Do not mirror the form layout directly into database tables.

### Step 3: Add or confirm the relational schema

Create a forward-only migration with:

- Primary and foreign keys
- Tenant constraints
- Stable public IDs
- Unique business constraints
- Status checks
- Indexes
- Updated-at triggers
- RLS policies

### Step 4: Register the form

Seed `fastfield_forms` with:

- Form ID
- Name
- Unique purpose
- Explicit field mappings
- Notes identifying the validated form version

### Step 5: Create a dedicated mapper

The mapper must:

- Accept raw JSON and configured mappings
- Return a typed domain input
- Normalize values
- Validate required fields
- Preserve meaningful distinctions between blank, not applicable, and failed

### Step 6: Create a reusable domain service

The persistence service must be usable by both:

- FastField ingestion
- BoilerOps administration

Define deterministic matching rules before inserting records.

### Step 7: Add purpose routing

Update `ingestFastFieldSubmission()` and reprocessing so the new purpose uses
the dedicated mapper and service.

Return typed entity IDs and processing results.

### Step 8: Add the outbound projection

Configure or implement the corresponding FastField Data Table projection:

- Site Info
- Inspection Info
- Device Info

Ensure every row contains the stable BoilerOps ID used for future updates.

### Step 9: Add administration

Provide:

- List and detail views
- Create/edit controls where appropriate
- Sync status and retry
- QR controls for QR-addressable entities
- Clear validation and error messages

### Step 10: Verify the complete lifecycle

Test:

- First submission creates one record
- Duplicate delivery does not create another record
- Update submission changes the existing record
- Unknown BoilerOps IDs are rejected
- QR URL remains stable after edits
- Failed sync does not lose the Supabase record
- Retry changes failed/pending sync to synced
- Tenant boundaries are enforced

## 15. Adaptation Notes

### Inspection Info / inspectable target onboarding

- Target types are `boiler` and `plant`.
- Persistent records belong in `inspection_targets`.
- Type-specific details belong in `boiler_target_details` or
  `plant_target_details`.
- FastField rows use stable `bo_targetid`.
- A target is not a completed inspection event.

### Device Info onboarding

- Persistent physical devices belong in `safety_devices`.
- Devices link to `inspection_targets`.
- FastField rows use stable `bo_deviceid`, `bo_targetid`, and `bo_siteid`.
- Manufacturer/model/serial matching must not silently merge uncertain
  physical devices.

### Inspection submission

- Completed events belong in `inspections`.
- Activated report sections belong in `inspection_tests`.
- Devices participating in each section belong in
  `inspection_test_devices`.
- One test/report section may contain multiple devices.
- Raw attachments and report files must retain submission provenance.

## 16. Definition of Done

A new FastField submission implementation is complete only when:

- A real payload has been captured and documented
- The form is registered with a unique purpose
- The mapper is typed and validated
- Raw payload storage is immutable
- Domain persistence is idempotent
- Update matching is deterministic
- Stable BoilerOps IDs are returned to FastField
- QR behavior is implemented where required
- Outbound sync status is observable
- Admin management and retry paths exist
- Create, duplicate, update, failure, and retry scenarios pass
- Production environment configuration is documented
